## 1. Overview & Core Philosophy

In an enterprise identity and post-quantum cryptographic infrastructure, credential and key loss scenarios must have deterministic, zero-downtime recovery paths that preserve mathematical integrity. 

This document defines the complete operational and disaster recovery protocols for:
1. **Multi-Factor Authentication (MFA / 2FA)** lifecycle and device transfers (e.g., administrator upgrades/buys a new phone).
2. **Account Password Resets** across all three organizational roles (`Clerk`, `Mod`, `Root`) without relying on public email relays.
3. **Gateway Access Key Rotation** (`REVOKE_API_KEY`, `VERIFICATION_API_KEY`) via zero-downtime dual-key phasing.
4. **Post-Quantum Cryptographic (PQC) Key Resiliency** (ML-DSA-65 private keys, encrypted envelope backups, cold storage, and ledger continuity).
5. **Offline Break-Glass CLI Protocols** for catastrophic lockout scenarios.

## 2. Multi-Factor Authentication (MFA) & Device Migration

All internal dashboard users (**Root** and **Mod**) are strictly mandated to enforce Multi-Factor Authentication via **TOTP (RFC 6238)**. Help Desk clerks can be configured for MFA or password-only based on organizational counter policy.

### 2.1 Supported Authenticators (100% Offline)
- Mobile Authenticators: Google Authenticator, Microsoft Authenticator, Apple Keychain, Authy.
- Hardware & Desktop: YubiKey Authenticator (OATH-TOTP), 1Password, Bitwarden.
- **Air-Gapped Compatibility:** TOTP relies solely on synchronized system time (Unix epoch) and a shared HMAC secret. Zero outbound internet connectivity is required.

### 2.2 Scenario: Administrator Buys a New Phone (Graceful Migration)
No administrator should ever require server shell access or service restarts to migrate their TOTP token to a new mobile device.

```

                  │          Admin Buys a New Phone              │

        │                                │                                │
```

#### Step-by-Step Procedure:
1. **Initiate Transfer:** The administrator logs into the Internal Ops Dashboard normally using their current credentials.
2. **Access Security Profile:** Navigate to **User Profile $\rightarrow$ Security Settings $\rightarrow$ Transfer MFA Device**.
3. **Re-Authentication Prompt:** The administrator enters their current account password to authorize the change.
4. **Enrollment QR Display:** A new Base32 secret and QR code are dynamically generated in-memory.
5. **Verification Step:** The administrator scans the QR code with their new phone, types the 6-digit TOTP code generated by the *new* device, and clicks **Verify & Save**.
6. **Atomic Replacement:** The backend atomically replaces the active TOTP secret in the database, immediately invalidates the old device token, and generates 8 fresh single-use backup recovery codes.

### 2.3 Single-Use Emergency Recovery Codes
Upon initial MFA enrollment and whenever an MFA device is transferred:
- The system generates **8 single-use recovery codes** (formatted as `XXXX-XXXX-XXXX`).
- Codes are hashed using `scrypt` / `argon2id` before database storage; plaintext codes are displayed **once** to the administrator to download or print for physical safe storage.
- If a mobile device is damaged, lost, or wiped before migration, the administrator logs in by entering their username, password, and any unused recovery code in place of the 6-digit TOTP token.

## 4. Gateway Key Lifecycle: Zero-Downtime Dual-Key Phasing

### 4.1 The Vulnerability of Single-Key Configurations
Hardcoding a single `REVOKE_API_KEY` or `VERIFICATION_API_KEY` in static environment files forces operations teams to restart Docker containers whenever a key is rotated, causing service drops and immediately breaking downstream automated scripts.

### 4.2 Dual-Key Rotation Architecture (Active + Grace Key)
`verification-api` implements **Dual-Key Phasing** for administrative gateway endpoints:

```
[ State 1: Normal Operation ]
  Primary Key (Active):    "rev-key-alpha-2026-xyz" (Used by active systems)
  Secondary Key (Grace):   None

[ State 2: Root Triggers In-Dashboard Rotation ]
  Primary Key (Active):    "rev-key-bravo-2026-abc" (Issued immediately to caller)
  Secondary Key (Grace):   "rev-key-alpha-2026-xyz" (Accepted for 24-48 hr grace period)

[ State 3: Grace Period Expiry (Automatic or Manual Revoke) ]
  Primary Key (Active):    "rev-key-bravo-2026-abc"
  Secondary Key (Grace):   REVOKED & PURGED
```

### 4.3 Key Management via Root Console
- Root navigates to **Dashboard $\rightarrow$ Access & Key Management $\rightarrow$ Rotate Gateway Key**.
- Root selects target (`REVOKE_API_KEY` or `VERIFICATION_API_KEY`) and specifies the **Grace Window** (default: 24 hours).
- The system generates a cryptographically secure 256-bit hexadecimal string via CSPRNG (`crypto.randomBytes(32)`), commits the new primary hash and moves the previous primary to secondary status in SQLite, and logs the event to the audit trail.
- **Zero container restarts are required.**

## 5. Post-Quantum Cryptographic (PQC) Key Resiliency

The cryptographic trust root of ScatterID relies on NIST FIPS 204 **ML-DSA-65 (Dilithium3)** digital signatures. Loss of the active private key prevents issuing new credentials; loss of historical public keys prevents verifying existing credentials.

### 5.1 Encrypted Key Vault Snapshots (Cold Storage Export)
To guarantee that hardware corruption, hypervisor crashes, or storage degradation cannot permanently destroy key material:
1. **Automated Envelope Encryption:** Whenever keys are rotated or initialized, `crypto-service` generates an encrypted envelope:
   ```
   scatterid_pqc_backup_<publicKeyId>_<timestamp>.enc
   ```
2. **Encryption Standard:** Encrypted using **AES-256-GCM** with key derivation via Argon2id. The master backup passphrase is known only to Root or split across key custodians.
3. **Envelope Contents:**
   - Active and historical ML-DSA-65 private keys.
   - Public keys and SHA3-256 public key IDs.
   - Key generation timestamps and KMS rotation sequence numbers.
   - HMAC-SHA256 integrity tag over metadata.

### 5.2 Advance Pre-Distribution Architecture (Primary Operational Standard)

To eliminate the risk of offline devices encountering unknown keys upon rotation:
1. **Pre-Staged Key Pool Ceremony:**
   - Root does not mint keys at the exact moment of cutover.
   - Future signing keys (e.g. `v2`, `v3`, `v4`) are pre-generated during secure key ceremonies 3 to 6 months in advance.
   - The public keys are bundled into standard verifier software updates and synchronization payloads.
2. **Local Device Keyring Pre-Staging:**
   - Verifier devices store these keys with status `"pre_staged"` and an `"active_from"` timestamp.
   - When a scheduled or emergency rotation triggers on the ledger, 100% of synced offline devices already possess the public key in their local storage.
   - **Result:** Zero friction, zero rejected credentials, and zero need for emergency connectivity.

### 5.3 Cryptographic Delegation Endorsement Protocol (Disaster Fallback)

**The Catastrophic Scenario:** If an attacker compromises the server key vault and invalidates *both* the active key and all pre-staged keys, the authority must mint an entirely fresh, un-staged key (`v_emergency_fresh`) on the spot.

Offline devices have never seen `v_emergency_fresh`. To prevent them from failing with `UNKNOWN_KEY_ID`, ScatterID implements **Cryptographic Delegation Endorsements**:

1. **Delegation Endorsement Token Generation:**
   - The outgoing or supervising key signs a cryptographically verifiable delegation token:
     ```json
     {
       "type": "ScatterID_Key_Delegation_Endorsement",
       "endorsing_key_id": "pqc-mldsa87-2025-v1",
       "delegated_key_id": "pqc-mldsa87-2025-emergency-v99",
       "delegated_public_key_hex": "4a7b... (2,592 bytes)",
       "valid_from": "2025-08-01T00:00:00Z",
       "valid_until": "2026-08-01T00:00:00Z",
       "reason": "EMERGENCY_ROTATION_PRESTAGED_POOL_COMPROMISED",
       "nonce": "f82b1c4e90a781",
       "signature_by_endorser": "9e1a... (4,627 bytes)"
     }
     ```
2. **Offline Verification Algorithm via Delegation Chain:**
   - When an offline verifier receives a credential signed by `emergency-v99`, it inspects the embedded delegation header.
   - The verifier performs a 2-step mathematical proof:
     - **Step 1:** Verifies that `endorsing_key_id` exists in its trusted local keyring and validates `signature_by_endorser`.
     - **Step 2:** Uses the endorsed `delegated_public_key_hex` to verify the credential's ML-DSA-87 signature.
   - **Result:** The offline verifier cryptographically validates the brand-new key through mathematical trust delegation **without internet access, without VPN, and without an emergency firmware push**.

### 5.4 Catastrophic Disaster Recovery Procedure (Cold Storage Restore)
If a server host is completely rebuilt or moved to a disaster recovery site:
1. Deploy fresh base infrastructure via `docker-compose.yml`.
2. Root logs into the freshly initialized dashboard console.
3. Navigate to **Key Management $\rightarrow$ Disaster Recovery $\rightarrow$ Restore from Backup**.
4. Root uploads the `.enc` snapshot file and inputs the master passphrase.
5. `crypto-service` decrypts the payload in memory, validates the public key hashes against the Hyperledger Fabric ledger, and atomic-writes the restored state to local key storage.
6. **Result:** Full operational continuity restored; zero historical credentials are invalidated.

## 6. Offline Break-Glass Emergency CLI

If all Root administrators lose their passwords, devices, and recovery codes simultaneously, physical/SSH access to the deployment host acts as the ultimate root of trust.

### 6.1 CLI Tool Specification: `tools/admin_cli.js`
The offline break-glass utility interacts directly with the local SQLite database without requiring an active HTTP server:

```bash
# Execute within the verification-api container or bare-metal environment:
docker compose exec verification-api node tools/admin_cli.js breakglass --username admin
```

### 6.2 Execution Mechanics:
1. Verifies physical execution context (exits immediately if invoked over HTTP).
2. Prompts for a new master Root password (enforces 16+ character complexity).
3. Generates a fresh Base32 TOTP secret.
4. Renders an ASCII QR Code directly in the terminal for immediate authenticator scanning.
5. Outputs 8 newly minted single-use emergency recovery codes.
6. Writes a high-priority `SECURITY_ALERT: ROOT_BREAKGLASS_EXECUTED` event directly to the audit log table.
