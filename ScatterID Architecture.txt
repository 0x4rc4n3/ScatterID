  ScatterID Architecture Analysis & Solution Report: Node Failure Recovery & State Synchronization 

  ## System Architecture Context

  ScatterID implements a decentralized, fault-tolerant identity architecture combining Post-Quantum Cryptography (PQC ML-DSA-65), Shamir’s Secret Sharing (SSS (k = 3,n = 5)), isolated SQLite storage nodes (node_1.db through node_5.db),
  and immutable transaction anchoring via Hyperledger Fabric.

  ## 1. Write-Path Resilience During Partial Node Unavailability

  ### Threshold Guarantee Mechanics (k = 3,n = 5)

  When 2 out of 5 storage nodes are offline (e.g., Node 4 and Node 5), the system maintains full operational availability for issuing and verifying credentials without degrading cryptographic security.

                            n = 5 Total Shards Generated
                          /    |     |      \        \
                        S_1   S_2   S_3     [S_4]   [S_5]
                         |     |     |       OFFLINE OFFLINE
                         v     v     v
               +-------------------------------+
               | Written to Online Nodes 1-3   |  => Reconstructable (3 >= k=3)
               +-------------------------------+
    
  1. Shard Dispatch Protocol:
      • The Verification API dispatches shard i to node i via POST http://shard-node-i:3000/shard.
      • Simultaneously, credential metadata (excluding secret shares) is replicated across active nodes to preserve record metadata visibility.
  2. Threshold Verification:
      • Write acknowledgment succeeds as long as at least k = 3 nodes successfully store their assigned Shamir share Sᵢ = (i,yᵢ).
      • Failure to reach 2 offline nodes generates a warning log without aborting credential issuance or blockchain anchoring.
  3. Hyperledger Fabric Anchoring:
      • After ≥3 shards are stored, the SHA3-256 hash of the credential payload (

  ) is committed to Hyperledger Fabric via AnchorProof(credentialId, dataHash, issuerId, timestamp).

  ## 3. Automated State-Reconstruction and Backfilling Protocol

  Once Δᵢ is computed, the auto-healing mechanism (healShards) executes in-memory reconstruction to generate and backfill the missing i-th share without exposing raw credentials to persistent disk storage outside the node boundary.

    +-----------------------------------------------------------------------------------+
    |                            Auto-Healing Workflow                                  |
    +-----------------------------------------------------------------------------------+
    
    [ Step 1: Query 3 Active Nodes ]
        Fetch Shards (S_1, S_2, S_3) for credential_id in Delta_i from online nodes.
    
    [ Step 2: In-Memory Secret Recovery ]
        Recover Secret (raw_bytes) using Lagrange Interpolation over Finite Field GF(2^256):
            f(x) = Sum_{j=1}^3 ( y_j * Product_{m != j} (-x_m / (x_j - x_m)) )
    
    [ Step 3: Re-evaluate Shamir Polynomial ]
        Calculate missing share S_i = (i, f(i)) for target Node i.
    
    [ Step 4: Local Write & Checksum Generation ]
        Calculate SHA3-256 hash H(S_i) and append SHA-256 checksum (S_i : Checksum_i).
        Execute SQLite Transaction:
            INSERT INTO shard_references (id, credential_id, share_index, share_value, share_hash, share_checksum)
    
  ### Protocol Execution Details

  1. Active Share Retrieval:
      • The healing worker queries k = 3 available nodes holding valid shares for credential id ∈ Δᵢ.
  2. Lagrange Interpolation over Finite Field:
      • Reconstruction evaluates polynomial f(x) at x = 0 using the 3 retrieved shares (x₁,y₁),(x₂,y₂),(x₃,y₃):


               k      -xₘ
    Lⱼ(0) =    ∏    ─────── pmod p
            m=1,m≠j xⱼ - xₘ
    
              k
    Secret =  ∑  yⱼ·Lⱼ(0) pmod p
             j=1
    
  3. Target Share Re-generation:
      • Once the secret payload is reconstructed in memory, the polynomial f(x) is evaluated at target index x = i:


                 k        k    i - xₘ
    yᵢ = f(i) =  ∑  yⱼ·   ∏    ─────── pmod p
                j=1    m=1,m≠j xⱼ - xₘ
    
  4. Atomic Database Insertion:
      • The recovered share Sᵢ = (i,yᵢ) and its computed SHA3-256 hash are written to Node_i.db inside an atomic transaction:
        BEGIN TRANSACTION;
        INSERT OR IGNORE INTO credentials (id, data_hash, algorithm, signature, prime_mod, required_shares, status, issued_at)
        VALUES (@id, @dataHash, @algorithm, @signature, @primeMod, @requiredShares, @status, @issuedAt);
        
        INSERT OR REPLACE INTO shard_references (id, credential_id, share_index, share_value, share_hash, share_checksum)
        VALUES (@id, @credentialId, @shareIndex, @shareValue, @shareHash, @shareChecksum);
        COMMIT;

  ## 4. Post-Synchronization Cryptographic Integrity Verification

  After backfilling missing shard rows, the node performs strict cryptographic verification against both local constraints and the Hyperledger Fabric ledger anchor before marking itself HEALTHY.

                      +-----------------------------------------+
                      |           Recovered Node i              |
                      +-----------------------------------------+
                         /                                   \
                        /                                     \
                       v                                       v
         +---------------------------+           +---------------------------+
         |   Local Integrity Check   |           |  Blockchain Ledger Audit  |
         +---------------------------+           +---------------------------+
         | SHA3-256(share_value)     |           | Fabric QueryProof(id)     |
         |   == share_hash           |           |   == local.data_hash      |
         | SHA-256(index-value)      |           | Status == 'active'        |
         |   == share_checksum       |           +---------------------------+
         +---------------------------+                         |
                       \                                       /
                        \                                     /
                         v                                   v
                      +-----------------------------------------+
                      |         Integrity Status: VALID         |
                      +-----------------------------------------+
    
  ### Integrity Verification Pipeline

  1. Local Hash Checksum Validation:
      • Re-calculate SHA3-256 over share_value:

    H         = SHA3-256 (share\_value)
     computed

     Assert 

    H         ≡ share\_hash
     computed

  .

  • Re-calculate SHA-256 checksum over ${share\_index}-${share\_value}:

    C         = SHA-256 (share\_index parallel "-" parallel share\_value)
     computed

     Assert 

    C         ≡ share\_checksum
     computed

  .

  2. Blockchain Ledger Hash Verification:
      • Evaluate QueryProof(credentialId) against Hyperledger Fabric:


    FabricRecord = chaincode.QueryProof (credentialId)

  • Assert FabricRecord.dataHash ≡ node.data_hash.
  • Assert FabricRecord.status ≡ "active".

  3. Status Metric Transition:
      • If all cryptographic checks pass, the node status is updated from SYNCING to HEALTHY via /health endpoint telemetry.
